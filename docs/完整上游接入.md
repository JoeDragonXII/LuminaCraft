# 完整 LightCraft 接入

当前入口是自有 LuminaCraft 主界面；点击“导入与归档”或“高级编辑 / 完整照片库”时按需启动完整 LightCraft 桌面 host + ui-egui + engine。完整源码保留，不以自有照片库的功能范围替代上游。

两个窗口通过持久 request/result 和工程恢复检查点交接。同库只有一个窗口持有写入权；返回更新高级显影，保留主界面 Retouch。虚拟副本以库路径 + photo id 识别。完整版导出回执可返回主界面；当前仅提供本地导出，Lumina API 发布入口已停用。

完整版切到另一照片库后，返回分别携带原工程参数和最后浏览库/选片。主界面图库跟随切换，已载入工程仍关联原库；再次高级编辑按活动工程照片的所属库打开。不同库即使原片路径和 photo id 相同也不混合参数。LUT 从工程所属库加载；已有降噪缓存可独立保存、双向登记并用于预览/导出，合成缓存的清理后重开测试通过，真实模型和原生降噪窗口尚待验收。GPU 重启已有启动失败注入测试，切库中途异常和两窗口同时结束恢复已有进程级证据，具体边界见 HANDOFF 和主界面交接收尾状态。

## 源码与许可证

- `vendor/lightcraft` 保留固定上游，不修改；来源 commit 为 `b3d392b4994ee99dc389890f006600769d0c4ff5`。
- `upstream/lightcraft` 来自该 commit 的完整 Git archive，包含全部受版本管理的 crates、apps、docs、assets、tools、packaging 和测试；不复制上游 `.git` 和生成产物。
- 许可证、NOTICE 和上游说明完整保留。LuminaCraft 选择遵循该源码的 MIT 许可；上游也提供 Apache-2.0。
- `src/upstream_desktop` 复制完整桌面 host 的 Rust 模块，来源是上游 `apps/lightcraft/src`。root Cargo 直接依赖 owned 副本的引擎/UI 等 crates；UI 内所有引擎依赖解析到同一副本，不混用两个 catalog 类型。
- craft-ui 为上游固定的 craft-libs Git 依赖，rev `5c874d51eeb3de70e735c8ce87a59a7dedd47675`，Cargo.lock 已锁定。

## 适配范围

`--advanced` 接入整个上游界面和命令注册表，包含照片库、导入预览、Add/Copy/Move、日期/自定义目录归档、文件命名、评级/关键词、普通/智能相册、堆栈、虚拟副本、自动导入、重定位、Lightroom 目录读取、显影、历史/版本、预设、蒙版、导出、控制通道和桌面服务。保留所有源码不表示每个上游功能都已逐项完成 LuminaCraft 验收；实际验收记录见 HANDOFF。

Windows 默认构建开启 GPU、denoise、SAM 对接。模型权重未随开发包提供，没有模型时按上游显示安装/下载入口；不将 mock 或接口声明为真实 AI 生成。HEIF、rawnind 等可选 feature 源码保留，但本构建未启用。其他平台 apps/CLI/MCP 源码保留，尚未构建为 LuminaCraft 的独立产品。

LuminaCraft 自有适配：

1. 改为 LuminaCraft 窗口和应用 ID；首次中文网格视图，默认不注入演示照片。读取 Windows 已安装的微软雅黑，不重新分发系统字体或使用改色的上游品牌图标。
2. 设置、日志、模型目录与默认照片库隔离到 LuminaCraft。显式 LUMINACRAFT_LIBRARY 优先，否则允许恢复用户通过设置打开的库；原 LightCraft 配置不会被采用。
3. 主界面按钮启动 `--advanced --handoff`，先释放同库写入权；完整版提供返回按钮，关闭后主界面重开库并合并参数。独立 `--advanced` 仍可启动，`--workflow` 是主界面的兼容入口。原人像、SKILL 流程和 Lumina API 功能保留。
4. 编辑仅改变 catalog/工程。引擎命令查询与执行均限制原 XMP 写入、已有原片重命名、已有文件夹/照片磁盘移动；自动 XMP 回写强制关闭，底层 sidecar writer 也拒绝写入。导入 Move 是用户明确授权的例外。移出/恢复、评级、堆栈等 catalog 操作正常可用。
5. native 导出 writer 用 create_new + sync，禁止覆盖已有文件；重名规划后出现竞争文件也拒绝覆盖。
6. 上游 Copy 原来只复制照片，现同时用已验证的独立复制归档 stem.xmp / fullname.ext.xmp 原文件；冲突按整个文件组选择名称，失败清理此次产生的目标，原文件保持。Move 在来源移除前增加字节比较。

对应 owned 差异主要位于 `engine/src/lib.rs`、`engine/src/cmd/mod.rs`、`engine/src/sidecar.rs`、`engine/src/import_move.rs`、`ui-egui/src/lib.rs` 和桌面 host。其他上游模块完整保留。

## 现有扩展与边界

`src/app.rs`、`src/library_ui.rs`、`src/library_workflow.rs` 为原工程窗口；旧 `docs/照片库交互对照.md` 仅描述这一旧 UI，不再用于列举默认主程序的缺失功能。`src/archive.rs` 是此前自有归档后端，测试仍保留，默认主程序使用上游导入实现。

只读 Lightroom import 支持什么字段，以固定上游的 `docs/lightroom-import.md` 和实际目录验收为准。没有真实旧目录，不报告评级、集合或 Adobe 编辑结果已完成真实迁移。原片传感器显影与浏览用内嵌预览继续区分。未向 Lumina 3002 写测试数据，未提交、推送或发布。
# 删除管理整合补充（2026-10-15）

本地 owned UI 的 Services 新增 delete_from_disk，由根项目 src/deletion.rs 提供 Windows IFileOperation 回收站服务；vendor 固定快照不改。完整版 Delete 打开范围选择，普通相册可单独移除成员，照片库移除仍使用可恢复的软删除；磁盘删除先生成固定选片计划，第二次确认后执行。只选虚拟副本拒绝磁盘操作，原始记录选中时统计同文件所有引用。主页面复用同一计划与回收实现。新控件及命令用于本地整合验收，不据此宣称与 Adobe 的整体功能／画质完全等价。

Windows COM FFI 仅在根项目删除模块，不进入 owned 上游禁止 unsafe 的 crate；Windows crate 为已使用版本 0.62.2 的直接依赖。网络路径、链接、缺失／变化来源以及受打包清单约束的内嵌原片拒绝删除。恢复档案和测试图片保持私有，用户原片只在明确二次确认时移入回收站，原 XMP 不修改。说明见 docs/照片删除与移除.md。
